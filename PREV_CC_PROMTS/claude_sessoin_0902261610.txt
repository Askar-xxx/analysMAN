❯ А зачем нужна таблица teams? 

● Таблица teams — это кэш данных о командах из TheSportsDB API (endpoint
  lookupteam).

  Как работает:
  - При sync матчей скрипт получает home_team_id и away_team_id
  - По этим ID можно запросить подробности о команде через
  lookupteam.php?id=133604
  - Чтобы не дёргать API каждый раз — результат сохраняется в таблицу teams с
  TTL 24 часа
  - При повторном sync, если команда уже в кэше и cached_at < 24h — API не
  вызывается

  синхронизации.

❯ Хорошо, а зачем нужен raw_json?  

● raw_json — это полный оригинальный JSON-ответ от TheSportsDB API для каждого
  матча/команды, сохранённый «как есть».

  Зачем:

  1. Страховка от потери данных. API возвращает ~50 полей на матч, а мы парсим и
   сохраняем только ~15. Если завтра понадобится новое поле (например,
  TV-трансляция, погода, ссылка на превью) — не нужно заново запрашивать API,
  можно перепарсить из raw_json.
  2. Смена/обогащение промпта. Если решишь передавать больше данных в анализ —
  сырые данные уже в БД, просто пишешь новый парсинг.
  3. Отладка. Если матч сохранился с некорректными данными — можно посмотреть,
  что именно вернул API, и найти ошибку в парсинге.
  4. Миграция между API. Если сменишь провайдера — старые данные не потеряны,
  можно сравнить форматы.

  Минус: занимает место в БД (~2-5 КБ на матч). Для вашего масштаба
  (десятки/сотни матчей) — это несущественно.

  По сути, raw_json — это принцип «сохрани всё, парси что нужно сейчас».

     План: Интеграция H2H + таблицы в sync и промпт

     Контекст

     Сгенерированные анализы абстрактные — нет реальных данных о личных
     встречах, позициях в таблице, форме команд. TheSportsDB API (бесплатный
      ключ) предоставляет:
     - H2H (searchevents.php) — до 25 личных встреч со счётами, без
     ограничений
     - Таблица (lookuptable.php) — позиция, очки, форма (strForm), разница
     мячей; ограничение: только топ-5 команд лиги

     Архитектура должна быть масштабируемой: при смене API меняется только
     fetcher + parser, форматтеры и промпт остаются.

     Архитектура (3 слоя)

     [API fetch] → raw JSON → [DB storage] → [Formatter] → текст для промпта
      → [CONTEXT_FIELDS]

     - Слой 1 (fetch): привязан к конкретному API (TheSportsDB). При смене
     API — переписывается только этот слой.
     - Слой 2 (storage): raw JSON в БД — API-agnostic хранение.
     - Слой 3 (formatter): конвертирует raw JSON в читаемый текст. При смене
      API — адаптируется парсинг JSON, но формат вывода остаётся.
